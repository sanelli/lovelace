# Roadmap 2.013: generic specializations

**Objective:** Allow **specializations** of generic types/APIs for particular type arguments. Even when users declare `List<T>` with one default implementation for all `T`, they may **redefine** the implementation for a specific `T` — e.g. `List<Boolean>` may use a different representation and expose **additional** methods (typically **not fewer** than the general `List<T>` API, so substitution stays sound — exact rules TBC).

Prerequisite: [2.007](2.007-roadmap-templates-generics.md); overload/override/mangling and variance from [2.009](2.009-roadmap-overload-override-mangling.md); interfaces/traits from [2.008](2.008-roadmap-inheritance-traits-interfaces.md) may constrain what a specialization must provide.

## In scope

- Syntax to declare a specialization for concrete (or constrained) type arguments
- Rules for API compatibility with the unspecialized generic (extra methods OK; removing/weakening TBC — prefer “not less”)
- Lowering / monomorphization interaction (which body is picked)
- Name mangling / identity of specialized vs general forms
- Samples + tests (e.g. bit-packed `List<Boolean>` vs general `List<T>`)

## Out of scope

- Defining generics themselves → [2.007](2.007-roadmap-templates-generics.md)
- Shipping specialized Augusta containers → [3.005](3.005-roadmap-augusta-libraries.md) (consumes this feature)
